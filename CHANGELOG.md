## 0.4.1 - 2026-10-12

- Security (policy layer): caveats on the root grant outside the envelope are now evaluated like delegated caveats; new policy_caveats/evaluate_caveats helpers (incl. max_spend). The core verifier still does not evaluate caveats. Ruby API: `AtlasPca.policy_caveats(grant, chain)` and `AtlasPca.evaluate_caveats(caveats, ctx)` (returns `[ok, failed]`; total, fail-closed on unknown types; `max_spend`, `expires`, `not_before`, `rate`, `max_blast_radius`, `reversibility_max`, `delegation_depth`, `budget_alloc`). `verify_pcactn` and `RackMiddleware` still do not evaluate caveats: a resource server enforcing a grant's caveats calls `AtlasPca.evaluate_caveats(AtlasPca.policy_caveats(grant, chain), ctx)` with its own action params. Corpus: `primitives.caveat_eval` (41, incl. the `r041-root-max-spend-exceeded` / `-within` pair) in `conformance.rb` and `test/test_r041.rb`.
- Threshold share signatures are validated per suite at the wire stage (was a fixed 64 bytes): absent `alg` = ed25519 (64-byte `sig`, no `pq_sig`), `ml-dsa-65` (3309-byte `sig`, no `pq_sig`), `hybrid-ed25519-ml-dsa-65` (64-byte `sig` + required 3309-byte `pq_sig`); a non-string / null / unknown `alg` is a wire failure; a share's `pq_pk` is not judged by the wire (the threshold check owns it). A pure ML-DSA-65 share can now be carried. Corpus: 20 `r041-share-*` vectors; `conformance.rb` skips a vector whose `requires` names a suite this verifier does not implement (`ml-dsa-87`, `slh-dsa-sha2-128f`). Snapshot `test-data/reasons.tsv.gz` regenerated (additive only: new corpus vectors).
- `RackMiddleware`: the `PCA-Action` header goes through the new public `AtlasPca.decode_pca_header` (strict unpadded base64url, then STRICT UTF-8; nil on failure). It was already strict base64url; bytes that are not valid UTF-8 are now refused at the decode step with the 401 `PCActn header is not canonical base64url` (they reached the JSON parser before). A leading BOM is kept (the strict JSON parser refuses it). Corpus: `primitives.pca_header` (27).
- Usability: a PCActn built natively as a Hash from the library's own helpers verifies. `b64e` now returns a UTF-8 string (Base64 returns US-ASCII), and the wire's string-encoding gate (`utf8_string?`, used by `tree_ok?` for values and keys) accepts US-ASCII-tagged strings with valid 7-bit bytes (ASCII is a subset of UTF-8). Before, such a PCActn failed the wire check. BINARY and other encodings, and invalid bytes (including a US-ASCII-tagged string with a high byte), are still refused.
- Version: there is no gemspec in this directory (the release version is the git tag); this entry is 0.4.1.

## Unreleased (BREAKING)

- Depth caps (security, parity): the canonical form (`canonicalize` / `hash_canonical`, and so every capability, grant and Merkle-leaf hash) refuses containers nested deeper than `MAX_JSON_DEPTH` (32, the outermost is depth 1) before recursing, like the reference `canonicalizeStrict`. Before, a correctly signed hop whose caveat nested past 32 levels verified (the reference refuses it), and a 100000-deep caveat, grant or `trusted_root` raised `SystemStackError` straight out of `verify_chain` / `verify_pcactn` (it is not a `StandardError`, so the R6-05 totality wrappers missed it). The loose parser (conformance-file reading only) turns a stack overflow into `Malformed`.
- R6-01: Rack body mode strict-parses the WHOLE `{"pcactn": ...}` body with the cap of 32 (the envelope counts, as the reference `defaultExtract`) and refuses duplicate keys anywhere; now pinned by tests.
- R6-05: `signer_set_hash` returns nil (fail-closed) for a string that is not valid UTF-8 instead of raising `Malformed`.
- R6-03/R6-04 (security, parity): `verify_threshold_share` validates the WHOLE signer set exactly like the TypeScript reference before looking at the share (`signer_registry`): known roles only (case-sensitive), canonical 32-byte `publicKey`, a present `pq_pk` (JSON null is present) must be canonical base64url of a registered PQ key length, one key per role, one role per key, and a duplicate (role, key) entry only with the same `pq_pk` (it was first-wins). `share['role']` must equal the role. Corpus: `primitives.threshold_set`, `primitives.signer_set_hash`.
- R6-05 (robustness): `verify_chain`, `verify_threshold_share` and `verify_pcactn` are total: malformed input of any shape is a refusal, never an exception. `verify_chain` applies the reference `wellTyped` hop check (string id/issuer/holder/body_digest/sig; absent-or-string alg/pq_pk/pq_sig/holder_pq/parent; caveats an Array of Hashes with a String `type`), so a correctly SIGNED but ill-typed hop is refused (it was accepted). Corpus: `primitives.malformed`.
- R6-02 (security): a signer-set role that registers a `pq_pk` now REQUIRES a PQ (pure or hybrid) threshold share; an ed25519-only share for that role is refused, so an Ed25519 break no longer forges a hybrid-registered role (parity with the TypeScript reference). Corpus: `agent-bound-signerset-with-pq-pk` is now `valid:false`; new positive `agent-hybrid-signerset-with-pq-pk`.
- R5-A1 (security): threshold-share verification is now signer-set PINNED, no longer self-vouched. The share must be for the one key the signer set registers for its role, a PQ/hybrid share verifies only under the set's registered `pq_pk` (a differing share `pq_pk` is refused), the share-suite tag is part of the signed bytes (a classical share cannot be relabelled hybrid), and the signer-set hash now includes a registered `pq_pk` (parity with the TypeScript reference). New corpus vectors: `agent-not-in-signer-set`, `agent-bound-signerset-with-pq-pk`, `agent-hybrid-relabel-*`.

- Suite policy defaults documented: no list = no restriction, an empty list refuses everything, and the hosted API defaults to ed25519 + Ed25519 hybrids (README lists the exact list to pass offline).

- R4-01: `AtlasPca.verify_chain` now takes the root's PQ authority from the verifier, exactly like the TypeScript reference (R3-01). Two new trailing arguments, `pq_pins` (Hash: root issuer Ed25519 b64u => PQ public key) and `trusted_root` (the verifier's own stored root capability). A non-ed25519 (pure `ml-dsa-65` or hybrid) ROOT hop is accepted only if `pq_pins[root['issuer']]` equals the root's `pq_pk`, or `trusted_root` is the root itself (same content hash). Otherwise it is refused with `hop 0: root suite '<alg>' needs a PQ key pinned for the root issuer (policy.pqPins) or the verifier's stored grant (policy.trustedRoot); the root's own pq_pk proves nothing about who issued it (R3-01)`. Before, a pure-PQ root signed with the attacker's own ML-DSA key but naming a victim Ed25519 issuer verified. Callers of `verify_chain` on a root they did not load from their own store must now pass `pq_pins`. `verify_pcactn` is unchanged in behaviour (it passes its grant as `trusted_root`). Internally one `resolve_pq_key` choke point mints the only key type (`PinnedPq`, private constructor) that `verify_suite` accepts, so the PQ verify cannot be called with an artifact key.
